# 과제 요구사항

# 1. 설계 및 API 문서 작성

코드를 짜기 전에, 무엇을 어떻게 만들지 먼저 문서로 정리하는 단계입니다.
문서는 두 개만 씁니다. 길게 쓸 필요는 없고, 처음 보는 사람이 읽고 "이대로 만들면 되겠다" 싶을 정도면 충분합니다.

## 작성할 문서

본인 디렉토리 아래 `docs/` 폴더를 만들고 안에 둡니다.

```
student-a/docs/        (student-b도 동일)
├── design.md
└── api.md
```

### design.md — 설계

요구사항을 보고 본인이 판단했을 때 필요한 기능을 리스트업하고, 각 기능에 어떤 로직이 쓰일지 간단히 적습니다. 코드 수준으로 자세히 쓸 필요는 없고, 한두 줄이면 충분합니다.

요구사항에 정해져 있지 않아서 직접 판단해야 하는 부분(예: 옵션이 없는 상품의 재고 처리, 비회원 장바구니 구분, 마감 여부 판단 기준)은 해당 기능의 로직에 어떻게 정했는지 함께 적어 주세요.

이런 식으로 씁니다.

```markdown
## 주문
- 장바구니 상품 구매
  - 장바구니의 각 항목에 대해 마감 여부와 재고를 확인한다.
  - 하나라도 통과하지 못하면 전체 주문을 실패 처리한다.
  - 통과하면 재고를 차감하고 주문을 저장한다.
```

### api.md — API 명세

- admin과 user로 나눠서 정리합니다.
- API마다 아래 내용을 적습니다.
    - HTTP 메서드와 URL
    - 한 줄 설명
    - 요청 예시(경로, 쿼리, 본문)와 응답 예시
    - 실패하는 경우와 그때의 상태 코드 (예: 재고 부족, 마감된 프로젝트)
- 처음부터 모든 API를 완벽하게 정의할 필요는 없습니다. 목록을 먼저 만들고 예시를 채워 나가세요.

## 작업 방식

1. 본인의 `student-x/dev`에서 `student-x/docs-design` 브랜치를 만듭니다.
2. 문서를 작성하고 커밋합니다. 예: `docs: 설계 문서 추가`, `docs: API 명세 추가`
3. 브랜치를 push하고, `student-x/dev`로 PR을 올립니다.
4. 상대 학습자의 리뷰를 받은 뒤 Squash and merge로 병합합니다.

작업은 본인 디렉토리 안에서만 합니다. 브랜치와 PR 규칙의 자세한 내용은 컨벤션 문서를 참고하세요.

# 2. 구현

1단계에서 작성한 설계 문서(`design.md`)와 API 명세(`api.md`)대로 구현하면 됩니다.
문서에 적은 기능과 API를 빠짐없이 만들고, 코드는 컨벤션 문서를 따라 주세요.
구현하다가 설계가 바뀌면 문서도 같이 고칩니다.

## 작업 방식

기능 단위로 브랜치를 나눠서 작업하고, PR은 본인의 `student-x/dev`로 올립니다.
브랜치와 PR 규칙은 컨벤션 문서를 참고하세요. 작업은 본인 디렉토리 안에서만 합니다.

## 구현이 끝나면

구현이 완료되면 **유효석 멘토**에게 연락해서 Swagger 사용법을 배우고, Swagger로 직접 테스트까지 진행합니다.
